## 参照元・関連情報の必須添付ルール（RULE-LINK-IMG-REQUIRED）

**すべての投稿（メイン・リプライ）に参照元リンクまたは画像を必ず添付すること。**

- **メイン投稿**: og:imageが取得できた場合はネイティブ画像として添付。og:imageが取得できなかった場合は参照元URLを本文末尾（「詳細はリプ欄へ」の直前）に「参考: URL」として追加。どちらも不可能な場合は投稿をスキップして別の記事を選び直す。
- **リプライ投稿**: replyUrlで参照元URLが自動付与される。さらに、リプライ本文中にも関連URL（公式発表ページ、論文、データソース、関連ニュース記事等）を1〜3個含めること。関連URLが見つからない場合でも最低限参照元URLをリプライ本文中に明記する。
- **画像もリンクも無い投稿は絶対に実行しない。**

## 投稿フォーマット（必須）

### メイン投稿（250〜400文字）
- スマホ1画面で核心が伝わる長さ。文の長さにムラを出す（短い体言止め→長めの補足→また短く、のように不規則に）

- **冒頭フック（30文字以上）**:
  記事の核心を「自分の言葉で」書く。テンプレ的な煽り文句は禁止。具体的な固有名詞・数字・事実を含めること。
  良いフックの例（※トーンの参考のみ。丸コピー厳禁。毎回ゼロから書くこと）:
  - 「GPT-5 Turbo、推論87%短縮ってことはAPI単価もガクッと落ちるわけで」
  - 「Googleが方針転換した理由、調べたら思ったよりシンプルだった」
  - 「半年前に"まだ早い"って言ってた自分を殴りたい。現場はとっくに動いてる」
  - 「8時間→23分。最初は盛ってると思ったけど試したらマジだった」
  - 「中小のAI導入、コストがネックって話はもう古い。前提が崩れた」

- **文体は「業界を追ってる友人がリアルタイムで反応してる感じ」**:
  完璧な文章にしない。多少荒くていい。
  - 「〜なわけで」「〜ってことは」「〜なんだけど」等の口語的接続を自然に使う
  - 体言止め、倒置、途中で切る文を混ぜる。全文が「〜だ。」で終わらないように
  - 報告調（〜しました・〜されています・〜とのことです）は絶対禁止
  - 1文ごとに改行する「ポエム構成」にしない。2〜3文をまとめて書く箇所も作る
  - ニュースの要約ではなく「このニュースを見て自分はどう思ったか」を書く
  - 感想は具体的に。「すごい」「衝撃」ではなく、なぜそう思うかの理由込みで
  - **句読点は正確に打つ**。絵文字が文頭1個だけなので、句読点が読みやすさの命綱。文末は基本「。」で閉じる（体言止め・倒置で意図的に省く場合を除く）。読点(、)も適切な位置に入れてリズムを作る
  - **全部わかってる風に書かない**。「正直これがどう転ぶかはわからない」「自分の読みが合ってるかは微妙だけど」「ここは詳しくないから断言できないけど」のような不確実性を自然に混ぜる。「え、これマジか」「知らなかった」「見落としてた」のような驚き・発見のリアクションもOK

- 末尾は「詳細はリプ欄へ」で締める
- **引用・参照元URLはメイン投稿に必ず含める**。記事の出典を明示して信頼性を担保する。URLがない場合は引用元・参照元・関連する画像を極力添付して出典を補完する
- **画像添付**: og:imageに加え、引用元・参照元・関連する画像があれば極力添付する
- **重要**: メイン投稿で「詳細はリプ欄へ」と書いた場合、リプライで必ず詳細な説明を行うこと
- 絵文字：文頭に1個だけ（複数使用は逆効果）
- **文字数制限**: 250〜400文字（250字未満はシステムでブロックされる）

### AIっぽさ回避（投稿前に必ず確認し、該当したら書き直す）
- すべての文が同じくらいの長さ → リズムにムラを出す
- 「問題は〜だ」「重要なのは〜だ」「注目すべきは〜だ」が2回以上 → 1回まで
- 短文→改行→短文→改行が等間隔で続く → 段落にまとめる箇所を作る
- フック例やテンプレ例文をほぼそのまま使っている → ゼロから書き直す
- 「衝撃」「革命」「ゲームチェンジャー」「パラダイムシフト」等の大げさワード → 具体的な描写に置換
- 「これが意味することは大きい」「問題はここからだ」「準備はいいか？」→ AIの定型句。使用禁止
- 全文が断定調で「知ってる人が教えてあげる」トーン → 最低1箇所は不確実性・発見・驚きを入れる
- 読み返して「5分で雑に書いた感じがするか？」→ Noなら書き直し

### リプライ詳細（600〜800文字・ハッシュタグなし）
- **簡潔に、要点を絞って書く**。長ければ良いわけではない。読者が30秒で読み切れる量が理想
- **スマホで読まれる前提**。1段落は最大3文。段落間に空行を入れる
- **毎回同じ構成にしない**。以下のパターンからその記事に合うものを選ぶ:
  - **What→So What型**: 何が起きた→なぜ重要か→自分の見立て（3段落で完結）
  - **数字ドリブン型**: 核心の数字2-3個→比較で文脈づけ→示唆
  - **逆張り型**: 一般的な見方を提示→でも実は→根拠
  - **時系列型**: 背景→今回→今後の読み（流れが重要なニュース向け）
- **冒頭の「まず何が起きたかっていうと」は使用禁止**。毎回これで始まると読者は離脱する。核心から入る
- **「で、ここからが本題なんだけど」も禁止**。転換は文脈で自然に行う
- 1段落に専門用語を詰め込みすぎない。読み手が1回で飲み込める密度に
- **引用・参照元URLをリプライにも必ず記載する**（末尾に「参考: URL」）
- 不要な情報は削る勇気を持つ。「全部説明しよう」ではなく「これだけ伝われば十分」で書く

## 投稿プロトコル（2026-06-09改訂版）

### 本文可読性向上ガイドライン

**可読性3原則** を守るだけで、スキャンしやすく読者の関心を惹きつけられます。

1. **冒頭フック** – 1行でインパクトを与える。例: 「AI診断精度、ついに95%超え」や「生成AIが医療現場に持ち込む変革」など、読者がすぐに "何の話か" を判断できる文を書きます。
2. **段落分割** – `\n\n` で **3〜4段落** に区切ります。各段落は **30〜80字** 程度が目安です。空行は文字数にほとんど影響しませんが、タイムラインでの見やすさが格段に向上します。
3. **箇条書き** – 「・」で要点を列挙し視覚的に把握しやすくします。

このガイドラインに従うことで文字数は250〜400字の範囲内に収まり、タイムラインでスキャンしやすくなります。

### 文字数・構造要件

| 項目 | 本文（メインポスト） | リプライ（詳細解説） |
|---|---|---|
| 文字数 | **250〜400文字** | **600〜1000文字** |
| URL/画像 | **必須**（参照元URLを本文内に埋め込む） | **必須**（追加の参考URLまたは同URL再掲） |
| 構造 | **冒頭フック＋段落分け＋箇条書き**で構造化。末尾は独立行の「詳細はリプ欄へ」 | 見出し（■〜）＋箇条書き（・〜）で構造化 |
| ハッシュタグ | **全面禁止** | **全面禁止** |
| 絵文字・装飾記号 | 禁止 | 禁止 |

### 【絶対禁止】本文・リプライ共通

- **ハッシュタグ（`#AI` `#フィジカルAI` など、`#`記号を伴う全てのタグ）**
- 絵文字（😊🤖📌✅🎉🏥👇 等すべて）
- 番号付き絵文字（1️⃣2️⃣3️⃣ 等）
- 装飾記号の羅列（【】◆◇●○▶ 等）
- マークダウン記法（`**太字**` `` `コード` `` 等）

### 【必須要素】本文・リプライ共通

- **参照元URL（http/https）を必ず1つ以上埋め込む**
- 信頼性の根拠として、情報発信には必ずメディア（URLまたは画像）を明記する

### 【URL実在性】本文・リプライ共通（v19・最重要）

過去に「存在しないURL」「記事が無いURL」を投稿する事故が発生したため、以下を厳守する:

- **URLは必ず web_search / web_fetch で実際に開いて実在を確認したものだけを使う。** 推測・記憶・捏造でURLを書かない。
- **`https://example.com` 等のプレースホルダや `<URL>` 記法をそのまま残さない。** テンプレートのURL欄は必ず実在URLに差し替える。
- 検証は2段で自動化済み（迂回不可）:
  1. `validate.js` … `example.com`・`<URL>`・`/example` 等のプレースホルダ/壊れURLを **BLOCKING（exit 2）** で遮断。
  2. `post-to-x.js` の到達性プリフライト … 埋め込みURLを実フェッチし、**404 / ドメイン不在は BLOCKING（exit 2）**。401/403（Bot検知）は実在扱いで通過。
- 取得方針は CLAUDE.md 準拠（web_fetch → 401/JS壁は obscura `--stealth`）。

## 投稿の仕組み（全体構成）

```
cronジョブ
  → OpenClawエージェント
    → web_searchでネタ収集（参照元URLを取得）
    → 本文作成（250〜400文字＋URL埋め込み＋「詳細はリプ欄へ」で締める）
    → リプライ文作成（600〜1000文字＋見出し+箇条書き構造＋URL埋め込み）
    → exec: post-to-x.bat "本文" "リプライ文"
      → post-to-x.js（Playwright + Cookie認証）
        → ロック取得（同時実行防止 / logs/.post.lock）
        → 事前検証：ハッシュタグ・文字数・URL・不可視文字
        → Cookie 鮮度チェック（25日超で警告）
        → x.com/home でログイン状態判定（auth/rate-limit/challenge を分類）
        → ホームのツイートボックスに本文を入力・投稿
        → 投稿後のURLを取得
        → そのツイートを開き「返信」ボタンをクリック
        → リプライフォームにリプライ文を入力・投稿
        → 【v18.2 追加】投稿後検証：本文URL・リプURLを再訪してDOM確認＋スクショ取得
        →   成功 → VERIFY_TWEET:ok / VERIFY_REPLY:ok を stdout に追加出力
        →   失敗 → 警告イベント post_verify_failed を logs に記録（exit 0 維持）
        → 完了 → exitcode 0 + TWEET_URL / REPLY_URL / VERIFY_* を stdout 出力
        → 構造化ログを logs/post-YYYYMMDD.log に追記
```

### 単体投稿とリプライ付き投稿の使い分け

| モード | コマンド | 用途 |
|---|---|---|
| 単体投稿 | `post-to-x.bat "本文"` | 単発情報発信（URL必須） |
| **リプライ付き** | `post-to-x.bat "本文" "リプライ文"` | 本文を「詳細はリプ欄へ」で締め、リプ欄で深掘り解説 |
| **ドライラン** | `node post-to-x.js "本文" "リプライ文" --dry-run` | 検証だけ走らせ X には投稿しない。cron 登録前や新プロトコル適合確認に使う |
| **本文URL指定** | `node post-to-x.js "本文" "リプライ文" --url "<URL>"` | 本文中の「詳細はリプ欄へ」直前に URL を自動挿入 |
| **リプライURL指定（v18）** | `node post-to-x.js "本文" "リプライ文" --reply-url "<URL>"` | リプライ末尾に「参考: <URL>」を自動追記 |
| **リトライ無効化（v18）** | `node post-to-x.js "本文" "リプライ文" --no-retry` | ナビゲーション系エラーでもリトライしない（重複投稿リスクを徹底回避） |

## 投稿後検証（v18.2 / 2026-04-19 追加）

「投稿ボタンを押してトーストが出た」では実際にタイムラインに残ったかは保証できない。
レート制限・shadow ban の一部・ナビゲーション完了前のキャンセル・空本文の混入など、
**投稿が成功扱いなのに実体が無い** ケースを後追いで検出するため、投稿直後に検証ステップを走らせる。

### 検証フロー

投稿成功後、`browser.close()` する前に同じ Playwright セッション・同じ Cookie・同じ page で：

1. 取得済みの `tweetUrl` を再訪し、ページ本文を確認
2. ページ状態を分類：`deleted` / `not_found` / `rate_limit` / `ok`
3. `article[data-testid="tweet"] > [data-testid="tweetText"]` から本文DOMを取り出す
4. 状態問わず `logs/verify-tweet-{timestamp}.png` にスクリーンショットを保存
5. リプライURL がある場合は同じ手順で `verify-reply-*.png` も取得

### 出力

stdout には既存の URL 行に加えて検証ステータス行が追加される：

```
🎉 完了
TWEET_URL:https://x.com/KURAOpenclaw/status/...
REPLY_URL:https://x.com/KURAOpenclaw/status/...
VERIFY_TWEET:ok
VERIFY_REPLY:ok
```

`VERIFY_TWEET` / `VERIFY_REPLY` の値：
- `ok` — DOM上に本文が存在することを確認
- `fail` — 削除済み・存在しない・レート制限・本文DOM不在
- `error` — 検証中に例外（ネットワーク等）
- `none` — リプライが無い投稿（`VERIFY_REPLY` のみ）
- `skipped` — 投稿スキップ等で検証未実行

### ログイベント（logs/post-YYYYMMDD.log）

- `post_success` — 投稿そのものの成功（既存）。`extra.verifyTweet` / `extra.verifyReply` に検証結果を含む
- `post_verified` — 検証も含めて完全に成功（v18.2 新規）
- `post_verify_failed` — 投稿は成功したが検証で異常を検出（v18.2 新規・**警告イベント**）

### 終了コードの方針

検証失敗でも **exit 0 を維持する**。理由は：
- 投稿そのものは成功しており、cron 側でリトライすると重複投稿になる
- 検証失敗を `post_verify_failed` ログ + stdout の `VERIFY_*:fail` で下流（Discord 通知等）が拾えるようにする
- exit code を変えると既存の cron / バッチ統合が後方互換を失う

### 既知の限界

- **shadow ban の完全検出は不可**: ログイン済み自セッションでは自分の投稿は普通に見える。
  外部視点での非表示は検出できない。これを完全に解くにはログアウト状態の別ブラウザコンテキストが必要だが、
  shadow ban 判定ロジック自体が公式に定義されていないため意図的に実装しない。
- **検索APIによる二次確認は実装しない**: X の検索APIは有料化されており、
  非公式エンドポイントを叩く実装は ToS リスクが高い。

### ドライランとの関係

`--dry-run` フラグ時は投稿そのものが走らないので、投稿後検証もスキップされる
（早期 exit で `runPost()` まで到達しない）。

## 投稿手順（リプライ付き・標準フロー）

### ステップ1: 本文を作成する

- `web_search`でトピックの最新情報を収集する
- 収集時に**参照元の主要URL**を必ず1つ確保する
- 日本語 **250〜400文字**で本文を作成する
  - URL は X 上で 23 文字換算のため、残り 227〜377 字で本文を組み立てる
  - **トーン調整**: 会話調・ファクト重視。専門用語は最小限に。
  - **透明性の向上**: 本文冒頭に「AI発信」を明記する（例: 「AI発信: 〜」）
  - **ユーモアの見直し**: 軽いユーモアを含めるが、過度にしない（例: 「〜って、ちょっと驚いた」）
  - 構成：冒頭に事象の要点（1文）→ 中盤に具体的な数値・背景・ファクト → 末尾に業界への示唆
- **本文内に参照元URLを必ず埋め込む**（末尾近くに配置）
- **本文の末尾は必ず「詳細はリプ欄へ」で締める**（絵文字なし）
- **ハッシュタグ・絵文字・装飾記号は一切禁止**

#### 本文の可読性ルール（v18.1 / 2026-04-19 追加）

**可読性3原則**
1. **冒頭フック**: 1文で主題提示（質問・驚き・事実）。
2. **段落分割**: 空行で区切り、3〜4段落にする。
3. **箇条書き**: 「・」で要点を列挙し視覚的に把握しやすくする。

**推奨テンプレート**（約340字）:
```
AI診断精度、ついに95%超え。

最新の医学論文で、生成AIを用いた画像診断の精度が従来の医師より上回ったケースが報告された。

注目ポイントは3つ。
・肺がん・皮膚がん・網膜疾患の3領域で優位性確認
・医師の判断を補完する「第二オピニオン」として活用可能
・倫理的課題（バイアス・説明責任）はまだ解決途中

詳細はリプ欄へ
<実在を確認した参照元URL>
```
（↑ URL欄は必ず実在確認済みの記事URLに差し替える。プレースホルダのままだと BLOCKING で投稿されない）

タイムラインで読まれる本文は、**1段落ベタ書きではなくスキャンしやすい構造**にする。
リプライ側だけ「■見出し＋・箇条書き」で構造化されていて、本文だけ詰まった一塊だと、
そもそも本文が読まれずスクロールされてリプ展開まで到達しない。

**可読性3原則:**

1. **冒頭フック1行を立てる**: 1 行目で「何の話か／自分に関係するか」を判断できる短い導入。
   会話調・体言止め・問いかけのいずれかが効く（「〜って言葉、ここ半年で〜」「〜、ついに一段解けた。」など）。
2. **段落を空行（`\n\n`）で区切る**: 論点ごとに改行し、詰め込みを避ける。
   本文 250〜400字なら **3〜4段落** が目安。空行は数文字しか消費しないので 400 字上限を圧迫しない。
3. **並列要素は「・」付き短行で並べる**: 「ポイントは3つ」のような列挙はベタ文ではなく
   箇条書きで視覚化する（リプの構造化と同じ考え方を本文にも適用）。

**本文の推奨テンプレ:**

```
（冒頭フック1行：会話調／体言止め／問いかけ）

（本論1：背景や要点を2〜3文で）

（本論2：3点列挙なら「・」で並べる）
・ポイント1
・ポイント2
・ポイント3

（結びの一言／読者への問い）

詳細はリプ欄へ <実在を確認した参照元URL>
```

**「詳細はリプ欄へ」は独立行**に置く（前に空行）。末尾 URL は同じ行でも別行でもよい。

**カジュアル系（X で伸びるテンポ）の場合:** 体言止め・短文・問いかけを混ぜてリズムを作る。
ただし会話調すぎると信頼性が落ちるため、ファクト（数値・固有名詞・URL）は崩さず守る。

良い例（本文・段落分け＋冒頭フック＋箇条書き・約340字）:

```
AI診断精度、ついに95%超え。

最新の医学論文で、生成AIを用いた画像診断の精度が従来の医師より上回ったケースが報告された。

注目ポイントは3つ。
・肺がん・皮膚がん・網膜疾患の3領域で優位性確認
・医師の判断を補完する「第二オピニオン」として活用可能
・倫理的課題（バイアス・説明責任）はまだ解決途中

詳細はリプ欄へ
https://example.com/medical-ai-paper
```

悪い例 ①（読みにくい：1段落ベタ書き・冒頭フックなし）:

```
2026年6月9日、医学論文誌で生成AIを用いた画像診断の精度が従来の医師より上回ったケースが報告された。肺がん・皮膚がん・網膜疾患の3領域で優位性が確認され、AIが医師の判断を補完する「第二オピニオン」として活用可能であることが示された。倫理的課題としてバイアスや説明責任の問題はまだ解決途中で、今後の研究が必要である。詳細はリプ欄へ https://example.com/medical-ai-paper
```

→ タイムラインで「文字の壁」に見えてスクロールされる。プロトコル（文字数・URL・リプ誘導）は満たしているが、可読性3原則を全て破っている。**冒頭フック・段落分け・箇条書きで視覚的に区切ること**。

悪い例 ②（プロトコル違反：絵文字・ハッシュタグ・装飾記号混入）:

```
【速報】AI診断精度95%突破！🎉
1️⃣ 肺がん・皮膚がん・網膜疾患で優位性
2️⃣ 医師の補完ツールとして活用可能
詳細はリプ欄へ👇 #AIヘルス #医療AI
```

→ ハッシュタグは BLOCKING（exit 2）。絵文字・装飾記号も全面禁止。

## 事前検証ルール（post-to-x.js v18 / validate.js v18）

投稿実行前に `validate.js` の `validateContent()` が以下を自動検証する:

| チェック項目 | 挙動 |
|---|---|
| ハッシュタグ（`#` + 英数/CJK / 単語境界判定） | **BLOCKING — exitcode 2 で中断** |
| 本文が 250〜400字の範囲外（X 実測ベース） | **WARNING（stderr）**、投稿は継続 |
| リプライが 600〜1000字の範囲外（X 実測ベース） | **WARNING（stderr）**、投稿は継続 |
| 本文にURL（http/https）が含まれない | **WARNING** |
| リプライにURLが含まれない | **WARNING** |
| **プレースホルダ/壊れURL（example.com・`<URL>`・`/example` 等）（v19）** | **BLOCKING — exitcode 2** |
| **埋め込みURLが 404 / ドメイン不在（到達性プリフライト・v19）** | **BLOCKING — exitcode 2**（401/403 は実在扱いで通過） |
| Cookie ファイルが 25日以上前のもの | **WARNING**、投稿は継続（失効リスクを通知） |
| **不可視文字（ZWSP, BOM, RTL/LTR マーク等）混入（v18）** | **WARNING**（誤コピペで混入しがちな ZWSP/U+FEFF を検出） |

**設計方針:** 文字数・URL の範囲外は警告のみとし、投稿自体は遮断しない（運用初期の柔軟性確保）。
**ハッシュタグ混入のみ厳格にブロック**する（プロトコルの根幹のため）。

### v18 で強化された検出ロジック

- **ハッシュタグ regex を Unicode 単語境界ベースに強化**: `(?<![\w\/=?&.\-])(#[\p{L}\p{N}_]+)/gu` — `見出し#建設業` のような CJK 直後のハッシュタグも検出。`https://example.com#section` のような URL fragment は誤検出しない。
- **X 公式重み付き文字数を `computeTweetTrueWeight` として併記**: Latin-1=1, それ以外=2 の X 公式仕様。従来の閾値判定（実測ベース）は変更せず、参考情報として表示。
- **URL 検出で末尾の句読点・閉じカッコを境界として除外**: `...詳しくは https://example.com。` の末尾「。」を URL に含めない。
- **不可視文字検出**: `\u200B`〜`\u200F`, `\u202A`〜`\u202E`, `\u2060`〜`\u206F`, `\uFEFF` を WARNING として表示。

### 文字数カウントの意味論

X は URL を `t.co` で **23 文字に短縮**するため、`validate.js` も同じ前提で計算する:

```
実測文字数 = (本文 - URL) のコードポイント数 + URL個数 × 23
```

例: 本文 380字（うち URL 60字を1つ含む）→ 実測 380 - 60 + 23 = **343字**（範囲内）

長い参照URLを含めても X 上での文字数は短くなる。SKILL.md の「250〜400字」基準は
この X 実測ベースの値で判定される。

`computeTweetTrueWeight` は将来 Premium / 無料層の閾値切替候補として併記しているだけで、
現行の閾値判定には使っていない（互換性重視）。

### --dry-run モード

X に投稿せず、検証だけ走らせる。BLOCKING なら exit 2、それ以外は exit 0。

```
node post-to-x.js "本文" "リプライ文" --dry-run
```

cron に登録する前、プロトコル改訂直後、リハーサル目的での使用を推奨。

## v18 で追加された運用機能

### 構造化ログ（logger.js）

すべての投稿イベントを JSONL 形式で `logs/post-YYYYMMDD.log` に追記する。
深夜 cron で静かに失敗していたケースを翌朝確認できるようにするのが主目的。

ログ構造:

```json
{"ts":"2026-04-19T22:00:01.234Z","event":"post_success","mainHead":"NVIDIAが2026年...","tweetUrl":"https://x.com/...","replyUrl":"https://x.com/...","elapsedMs":12345,"exitCode":0}
{"ts":"2026-04-19T22:30:00.000Z","event":"validation_blocked","mainHead":"#AI最新...","exitCode":2,"elapsedMs":120}
{"ts":"2026-04-19T23:00:00.000Z","event":"auth_failure","exitCode":3,"errorMessage":"ログインページにリダイレクト"}
```

**機微情報の保護:** 本文プレビューは先頭 40 字までに制限。Cookie 値・AUTH_TOKEN は絶対にログに出さない。

**ログローテーション:** 起動時に 30 日超のログを自動削除（`logger.startupCleanup()`）。

イベント種別:
- `post_success` 投稿成功
- `post_failure` 投稿失敗（generic）
- `validation_blocked` BLOCKING 違反で中断
- `lock_collision` ロック競合で中断
- `auth_failure` Cookie 失効
- `rate_limit` レートリミット
- `challenge` reCAPTCHA / unusual login
- `cookie_stale` Cookie が 25 日超過

### ロックファイル（lockfile.js）

同時実行を排他制御する。`fs.openSync('logs/.post.lock', 'wx')` でアトミック作成。

- 既存ロックがあり 10 分未満なら **exit 6** で即座に中断（重複投稿防止）
- 10 分超過した stale ロックは自動削除して取り直す（cron が長時間ハング時の救済）
- プロセス正常終了・SIGINT・SIGTERM で自動解放
- ロック中身: `{"pid": 12345, "ts": "2026-04-19T22:00:01.234Z"}`

### 認証状態の早期分類（classifyAuthState）

`x.com/home` 到達後、URL とページ本文から以下を分類して即座に分岐:

| 分類 | 検出条件 | 終了コード |
|---|---|---|
| `auth` | URL に `/login` または `/i/flow/login` を含む | 3 |
| `challenge` | URL に `/account/access`, `/i/flow/consent` 等、または本文に「reCAPTCHA」「確認コード」「unusual login」 | 5 |
| `rate-limit` | 本文に「Rate limit exceeded」「過度なリクエスト」 | 4 |
| `ok` | 上記いずれにも該当せず | 続行 |

### 控えめリトライ（最大1回）

`isRetryableError()` で **ナビゲーション系・タイムアウト・ネットワーク系のみ** リトライする。

**リトライしないエラー:**
- 「テキスト入力が空（ペースト失敗）」
- 「投稿ボタン無効状態」
- 「投稿後のURL取得に失敗」
- 「トースト未検出」（投稿が成功している可能性があるため）
- 認証系・チャレンジ系・レートリミット（人手対応必須）

**リトライするエラー:**
- `Timeout`
- `net::ERR_*`
- `Navigation failed`
- `ホームのツイートボックスが見つかりません`（ページロード未完了）

`--no-retry` で完全に無効化できる（重複投稿リスクを徹底回避したい場合）。

### node.exe フォールバック（post-to-x.bat）

```bat

```

## Cookie管理

### 初回セットアップ / Cookie更新手順

Cookie（`auth_token` / `ct0`）は `.openclaw/.env` で管理する。

**Cookie取得手順：**

1. ChromeでXにログイン（対象アカウントで）
2. **F12** → **Application** タブ → **Cookies** → **https://x.com**
3. 以下の値をコピー：
   - `auth_token`（約40文字）
   - `ct0`（約160文字）
4. `.openclaw/.env` の以下の行を更新：
   ```
   AUTH_TOKEN=（取得したauth_tokenの値）
   CT0=（取得したct0の値）
   ```
5. Cookieファイルを再生成：
   ```
   node C:\Users\sawas\.openclaw\workspace\tools\x-poster\setup-cookies.js
   ```

## 技術的な注意点（ハマりやすいポイント）

### ① `/compose/post` は使わない

`x.com/compose/post` を開くとモーダルオーバーレイが展開され、
Playwrightの通常クリックが `#layers` div にブロックされる。
→ **`x.com/home` のツイートボックスを使う**

### ② `#layers` オーバーレイの無効化が必要

URL入力後にサジェストドロップダウンが `#layers` 内に展開される場合があり、
「ポストする」ボタンのクリックをブロックする。

→ **ボタンクリック直前に `#layers` を `pointerEvents:none` にして回避**

```javascript
await page.evaluate(() => {
  const layers = document.getElementById('layers');
  if (layers) {
    layers.style.pointerEvents = 'none';
    layers.style.visibility = 'hidden';
  }
});
```

### ③ `Escape`キーは使わない

Escapeを押すと「ポストを保存しますか？」ダイアログが出てフローが壊れる。

### ④ テキスト入力はクリップボードペーストを使う

`keyboard.type()`で長文を入力するとサジェストや改行が挟まることがある。
→ **`navigator.clipboard.writeText()` → `Ctrl+V`** でペーストする

### ⑤ ボタンとtextareaのselectorはホームとリプライフォームで異なる

| 場所 | 投稿ボタン | textarea |
|---|---|---|
| `x.com/home` | `tweetButtonInline` | 最初の`tweetTextarea_0` |
| リプライフォーム | `tweetButton` | 最後の`tweetTextarea_0`（index=-1） |

**リプライフォームのtextareaについて**
- replyボタン`.click()`後、フォーカスは自動的にリプライtextarea（最後の要素）に当たる
- textarea.click()を追加すると逆にfocusが外れるため呼ばない
- Ctrl+Vをそのまま押せばリプライtextareaにペーストされる

### ⑥ bird CLIは使わない

bird CLIは有料サービスのため使用禁止。

### ⑦ `tool-usage-log.md` を編集しない

cronジョブの自動実行中に `tool-usage-log.md` を編集しようとするとエラーになる。
X投稿タスクではこのファイルを一切触らない。

### ⑧ `post-to-x-pon.bat` は **DISABLED**（v18）

旧 `post-to-x-pon.bat` は第2引数として **Cookie ファイルパスを誤って渡し、それをリプライ本文として投稿してしまう致命的バグ**を抱えていた。v18 で `exit /b 1` するスタブに置き換えて無効化済み。代わりに必ず `post-to-x.bat` を使うこと。

```
【X投稿 @KURAOpenclaw - AI医療・ヘルスケア最新情報】
1. web_searchで「AI医療 2026」「ヘルスケア AI 最新」を検索し重要トピック1件を選ぶ。**参照元URLは web_fetch で実際に開いて実在・記事内容を確認したものだけを採用する**（401/403はBot検知なので実在扱いでOK、404や開けないURLは別ソースを採り直す）。**URLの推測・捏造・`example.com` 等のプレースホルダ使用は禁止**
2. 本文を作成（250〜400文字・参照元URLを本文内に埋め込む・末尾は「詳細はリプ欄へ」・ハッシュタグ/絵文字/装飾記号は一切禁止）
3. リプライ文を作成（600〜1000文字・見出し（■）+箇条書き（・）で構造化・参照URLを埋め込む・ハッシュタグ禁止）
4. exec: C:\Users\sawas\.openclaw\workspace\tools\x-poster\post-to-x.bat "本文" "リプライ文"
5. 成功→TWEET_URL/REPLY_URL を Discord 報告。失敗→exit code を見て対応分岐：
   - 2: プロトコル違反 → 内容修正のうえ再実行
   - 3: Cookie 失効 → `.env` 更新と setup-cookies.js 実行を Discord 通知
   - 4: レートリミット → 1時間以上待機してから再実行
   - 5: チャレンジ要求 → 手動対応を Discord 通知
   - 6: ロック競合 → 既に他ジョブが動いているのでスキップ
   - 1: 予期せぬエラー → エラー内容のみ報告しリトライしない
6. 【Threadsクロスポスト】X投稿成功後に同一内容をThreadsにも投稿:
   - threads_main = 本文から「詳細はリプ欄へ」を除去（500文字以内に調整）
   - threads_reply = リプライ文からスレッド番号（1/n等）を除去、500文字以内に収める
   - exec: C:\Users\sawas\.openclaw\workspace\tools\x-poster\post-to-threads.bat "threads_main" "threads_reply"
   - 成功 → THREADS_URL を Discord 報告
   - 失敗 → エラーコードを Discord 報告（X投稿は成功済みなのでリトライ不要）
   - **Threads投稿の失敗でX投稿を巻き戻さない**
```

**注意: bird CLIは有料サービスのため使用禁止。post-to-x.bat のみ使用すること。**

## Chromeプロセスクリーンアップ

スクリプト完了後、Playwright起動のChromiumプロセスが残留していないか確認し、あれば終了する:

```powershell
Get-Process -ErrorAction SilentlyContinue | Where-Object {
    ($_.ProcessName -match 'chromium|chrome') -and
    ($_.MainModule.FileName -match 'playwright|ms-playwright' -or $_.CommandLine -match 'playwright|--disable-blink-features=AutomationControlled')
} | ForEach-Object {
    Write-Host "残留Chromiumプロセスを終了: PID=$($_.Id)"
    Stop-Process -Id $_.Id -Force -ErrorAction SilentlyContinue
}
Write-Host "Chromeクリーンアップ完了"
```
